# Fictional 30-well U.S. fleet

`config/fleet/us_srp_30_wells.json` defines exactly 30 fictional wells: five each in `US_TX_MIDLAND`, `US_NM_DELAWARE`, `US_ND_WILLISTON`, `US_OK_ANADARKO`, `US_CO_DJ` and `US_TX_EAGLEFORD`. Regional names organize examples; parameters are not claims about real basins or operators. The deterministic generator is `scripts/build_phase3_fleet.py`.

The configurations vary depth and two-section rod taper, stroke length, SPM, four-bar dimensions, damping, plunger diameter, fluid density, gas fraction, viscosity, intake head, pressure boundaries, gear ratio and running efficiency. Values are illustrative engineering assumptions, not QRod-calibrated designs. All 30 passed schema and four-bar geometry checks and completed the forward engine warm-up. Each subsequently produced one complete good-quality synthetic Surface Dynacard and one solved inverse Downhole Dynacard. This is `SYNTHETIC_VALIDATED` self-consistency only; none earns `ENGINEERING_VALIDATED` without independent reference agreement.

The simulator backend loads the fleet and exposes `/fleet` plus fleet and site start/pause/resume/stop actions. Every running well has a separate `Engine`, `Sensors`, fault state, run ID and worker thread. The simulator UI now provides fleet and site control pages. A 30-well native MQTT benchmark exposed a serious throughput backlog, so continuous fleet operation is not accepted. `data/evaluation/phase3/future_split_manifest.json` reserves complete well configurations for future training, calibration and held-out-well evaluation; it has not been used for training. Per-well save/restore, batch scheduling, complete APM site hierarchy and full scenario dataset generation remain unfinished.
